# agile-inspector

*[English](README.md) / 日本語*

**プロダクトの意思決定を担うのは人間のチーム。AI はスクラムマスターの役割に徹する。**

Claude Code プラグイン / marketplace。専任のスクラムマスターがいない、アジャイルに
不慣れなチームでも、デイリースタンドアップ・バックログリファインメント・KPT振り返り・
スプリントの開始と締めを、型どおりに回せるようにする。**このプラグインの AI は進行と
記録に徹し、実装には立ち入らない。**

コードを誰が書くかは問わない。実装の多くが AI 経由になった今も、**何を作るか・いつまでに
約束するか・何をもって完了とするか**を決めるのはチームで、アジャイルが働くのはそこ。

課題管理のバックエンドは **GitHub Issues または Jira** から選ぶ
（`/agile:init` で決めて `.agile/config.yml` に残す）。Kanban / Sprint 両対応。

> **Issue をまるごと AI に自律実装させるオーケストレーション型のツールとは、目的が
> 異なる。** コードの大半を AI が書く時代でも、**期間を区切って目標を約束し、技術的な
> 判断を下して価値を届ける**主体はチームにある。このプラグインが引き受けるのは、
> チームがその判断に時間を使えるようにするための、進行と盤面の管理。

**プラグインが守らせるのは、チームが決めたことだけ。** WIP上限・完了の定義（DoD）・
スプリントの長さ・話す言語は、すべて `.agile/` に置かれ、リポジトリにコミットされ、
チームが直接編集できる。プラグインはそれに従うのであって、独自のルールを持ち込まない。

チャットで完結する操作はテキストで、複数を見比べる場面はローカルのビジュアルボードで扱う。

## バックエンド

**チームが既に使っているトラッカーをそのまま使う。** 課題データはローカルに持たず、
`.agile/` に置くのはチームの合意事項（モード・WIP上限・DoD・テンプレート）だけ。

| | 画面 | 状態の書き換え | 認証 |
|---|---|---|---|
| **GitHub Issues** | このプラグインが持つ（ローカルのビジュアルボード） | 行う | `gh` CLI |
| **Jira** | **Jira のものを開くだけ** | **行わない**（チームが Jira 上で動かす） | `acli`（ブラウザ認証） |

**Jira ではカラム移動をチームに委ねる設計**にしている。Jira の状態変更はワークフロー
遷移であり、「どの列へでも動かせる」という前提が成り立たないため ── 既存の遷移ルールと
競合させないための措置で、チームが普段 Jira 上で行っている操作をそのまま活かす。
**優先度・見積り・スプリントへの投入**も同様に、計画では Jira のバックログ画面を開き、
チームが並べ替え、プラグインは**結果を読み戻して確認する**。
**盤面の点検（WIP超過・滞留・補充）とセレモニーの進行は、どちらのバックエンドでも同じ
ように働く。**

機構の詳細は `plugins/agile/docs/backends/` にあり、**スキル本体はコマンドを一切持たない**
（`README.md` が契約、`github.md` / `jira.md` が実装）。

> **Jira 対応の検証範囲**: **team-managed プロジェクトで検証済み**。
> company-managed は未検証（インスタンスの用意に組織の管理者権限が要るため）。
> company-managed を検出した場合は `/agile:init` がその旨を伝えたうえで続行する。
> 動かない場合は Issue で報告してもらえると助かります。

### なぜトラッカーを直接使うのか（GitHub Issues の場合）

- **更新にコミット/PR不要**：Issue はコードの git ツリー外にあるので、カラム移動もクローズも
  リポジトリのコミット履歴には現れない。
- **多人数で割れない**：1 Issue = 1 オブジェクト。同時編集でコンフリクトしない・アサイン/通知が標準装備。
- **ソロでも使える**：将来チーム化しても同じ仕組みのまま。
- **`gh` CLI で操作**：MCP を常時ロードせず、コンテキスト消費ゼロ・決定的。

Jira 側も同じ方針で、**MCP を使わず `acli` と REST だけ**で動く。

## 収録プラグイン: `agile`

| スキル | 説明 |
|--------|------|
| `/agile:init` | ラベル21種（[一覧](#agileinit-が作るラベル一覧)）を作成し、ローカル設定 `.agile/config.yml`（モード・WIP上限・To Do下限・滞留日数）と課題テンプレートを生成、DoD を合意する。**再実行すると、既存のものには触れず足りないものだけ追加する** |
| `/agile:issue` | **単一の課題**（Story / Task / Bug）を追加/編集/削除。依頼文から種別を判定し、Story はペルソナ形式＋受け入れ条件(AC)、Bug は再現手順に整形する |
| `/agile:board` | **ボードの表示と状態遷移**。モードに応じたボード（sprint ならスプリントボード、kanban ならカンバンボード）を画面で開き、テキストでも要約。WIP点検・ラベル張替でカラム移動（起票のルールは持たず、頼まれたら `/agile:issue` に委譲してその場で実行する） |
| `/agile:backlog` | **バックログの表示と優先度変更**。優先度バケット別の一覧を出し、バックログ画面を開く。`#12 を high に` で `prio:*` を張り替え |
| `/agile:standup` | **デイリーの進行**。ボードを開き、Issues の状態＋直近コミット/マージPR から各自の「前回/今日」を先に埋めたうえで、sprint は1人ずつ・kanban はボードを右から左に確認して回る。ブロッカーを拾って締める |
| `/agile:refine` | **バックログ整理**（リファインメント）。`/agile:backlog` の画面を使って腰を据えて棚卸しし、優先度の付け直し・追加削除・分割・ACの明確化・ポイント見積もりまで行う**セレモニー**。週1回など定期的に実施（sprint モードならスプリント期間中に） |
| `/agile:retro` | **レトロスペクティブ**（KPT）の進行。**チームが使っている面**（内蔵の KPT ボード / 外部ホワイトボード / 会話）を開き、参加者が各自カードを書くのを Keep → Problem → Try と仕切る。前回の未完了 Try の確認、DoD 見直し、Try の作業 Issue 化、議事録まで行う。**kanban モードでも任意の周期で回せる**（sprint モードでは `sprint-close` から呼ばれる） |
| `/agile:sprint-start` | **【sprint 専用】スプリントプランニング**。次スプリントを作成し、**ゴールの草案 → それに照らした課題の選定 → ゴールの確定 → サブタスク分解**の順で進める。**担当は決めない** ── 引き受けた時点、つまりデイリーで決まる |
| `/agile:sprint-close` | **【sprint 専用】スプリントレビュー**。完了分のデモ用一覧・フィードバック→バックログ反映、振り返りは `/agile:retro` に委譲、積み残しは進捗メモを付けて`carried-over`ラベルでバックログへ戻す（次スプリントは開始しない） |

`sprint-start` / `sprint-close` の2つだけが sprint モード専用で、**残りは両モードで使える**。

入口は「**何に対して操作するか**」で分かれている ── 1件なら `/agile:issue`、ボードなら
`/agile:board`、バックログなら `/agile:backlog`、セレモニーはそれぞれ専用コマンド。

### セレモニー系は AI が司会をする

`standup` / `refine` / `retro` / `sprint-start` / `sprint-close` は、結果を1回出力して
終わるコマンドではなく、**AI が進行役として1ステップずつ確認しながら進める**。
スクラムマスターが不在のチーム、アジャイルに不慣れなチームでも、会議の型どおりに
進められるようにするため ── このツールの目的そのものがそこにある。

想定している使い方は、**チャット欄を読みながら、別ウィンドウのボードを見て進める**形:

```
ターミナル / Claude Desktop          ブラウザ（board-ui）
┌──────────────┐  ┌──────────────────────┐
│ AI が司会・記録  │  │ 担当者スイムレーン       │
│ 1人ずつ確認する  │  │ カードをドラッグで移動   │
└──────────────┘  └──────────────────────┘
```

AI は進行と記録に、人はカードの操作に集中する。ウィンドウの配置は OS 側の話なので
プラグインは関与しない（一度並べればそのまま使える）。

進行中に必要な画面は AI が自動で開く。ただし**開くかどうかはコマンドの種類ではなく
ステップごとに決まる** ── 例えば `refine` はバックログを開き、`sprint-start` は選定で
バックログ・分解でボードを開き、`sprint-close` はデモ一覧を出すだけの場面では何も開かない。

ビジュアルボード（ローカル Web アプリ）は独立したコマンドではなく、**上記のスキルが必要な場面で
自動的に開く**。3画面あり、使う場面で開き分ける。

| 画面 | 開くコマンド | できること |
|---|---|---|
| バックログ | `/agile:backlog`、`/agile:refine`、`/agile:sprint-start`（課題の選定） | 優先度バケット間のドラッグ、スプリントへの投入 |
| ボード | `/agile:board`、`/agile:standup`、`/agile:sprint-start`（サブタスク分解） | カラム移動、スイムレーンでの作業管理 |
| ふりかえり | `/agile:retro`、`/agile:sprint-close`（振り返り） | KPT カードの記入、Keep/Problem/Try 間のドラッグ |

バックログとボードは毎日使う画面だが、**ふりかえりはセレモニー中しか存在しない**。
振り返りは全員が自分のPCでカードを書くので、参加者も各自 `/agile:retro` を実行する
── 進行役の画面を見ているだけでは書き込めない。

**ふりかえり画面からは、バックログにもボードにも切り替えられない。** これは意図的な
制限で、会議中の操作で実際の課題が動いてしまうのを防ぐため。途中でバックログを見たく
なったら、スキルが別画面として開く ──
そちらは**バックエンドを知っている**ので、Jira なら Jira のバックログが開く。

### ふりかえりをどこでやるか

**バックエンドとは独立した軸。** GitHub のチームが FigJam を使いたいこともあれば、
Jira のチームがこのプラグインのボードを使いたいこともある。`/agile:init` で訊かれ、
答えは個人設定ではなく**チームの合意**として config に残る。

| `retro.board` | 中身 |
|---|---|
| `builtin` | 上の KPT 画面。**カードは作業のバックエンドに関わらず、このリポジトリの Issue として保存される** |
| `external` | チームが既に使っているホワイトボード（FigJam / Miro / Confluence）。**URL を開くだけで API は一切叩かない**。ラウンドが終わったらチームがレーンごとに貼る |
| `chat` | 画面なし。Keep / Problem / Try を会話の中で集める |

**Jira でも `builtin` は検討に値する。** Jira に KPT ボードは無く、実務では
Confluence のページを使うか、振り返り用の課題種別を作ってバックログの視認性を
下げる運用になりやすい。付箋を GitHub Issue として持てば **Jira 側は一切増えず**、
バックログは作業だけの状態を保てる。
付箋を GitHub Issue として持てば Jira 側は一切汚れず、採用された Try は
**Jira に**起票され、元の付箋へのリンクを背負う。`gh` の認証とリポジトリの Issue が
有効であることが条件で、満たさない場合は `external` が既定。

`external` ではこちらは何も保存せず、ホワイトボードの API も読まない ──
**連携手段はクリップボードだけ**。これは意図的で、どのツールでも動く（来年チームが
乗り換えた先でも）。

バックログとボードには**ヘッダーに「+ 作成」**があり、種別（Story / Task / Bug）を選んで
起票できる。データはスキルと同じものを直接読み書きするので、チャットと画面のどちらで
操作しても同じ結果になる。

### ボードとスイムレーン

「アジャイルボード」は総称で、その下に**スプリントボード**（期間で区切り、約束した分を
終わらせる）と**カンバンボード**（区切り無し、流れを止めない）がある。ルールが逆なので
1つのチームが両方を同時に使うことはない ── したがって `/agile:board` は引数を取らず、
`mode` を読んでどちらかを開く。

スイムレーンはボードのカードを横の行にグループ化する切り替えで、画面右上から1クリックで
変えられる（Jira の「グループ化」に相当）。**使えるレーンはモードで異なる。**

| モード | スイムレーン | 使う場面 |
|---|---|---|
| 共通 | **なし**（既定） | 素の盤面。まずここから始める |
| sprint | **担当者** | デイリースタンドアップ。誰が何を持ち、どこで詰まっているか、負荷が偏っていないか |
| sprint | **親課題** | 日中の進捗確認。ストーリー単位で「あと何が残っているか」を俯瞰する |
| kanban | **Expedite** | 特急 / 標準 / バックグラウンドの3レーン。障害・クリティカルなバグを通常タスクに埋もれさせない |

kanban に担当者レーンは無い ── カンバンは「手が空いた人が上から引く」プル型で、
人で横に割ると「どの列で詰まっているか」という肝心の流れが見えなくなるため。
列を動くカードはどのレーンでも**作業単位**（サブタスク、および分解されていない
Story / Task / Bug）で、分解済みの親は容器なので親課題レーンでは行の見出しになる。

## カラムの表現（GitHub Issues の場合・ラベル方式）

| ボードの列 | Issue の状態 |
|-----------|-------------|
| Backlog | open ＋ `status:*` ラベルなし |
| To Do | open ＋ `status:todo` |
| In Progress | open ＋ `status:in-progress` |
| In Review | open ＋ `status:in-review` |
| Done | **closed** |

列の名前は Jira に合わせている。**ラベル名もその表示に合わせて付けている** ── ラベルは
GitHub 上でも直接目に入るもので、そこには表示名に読み替えてくれる層が無いため。

Sprint モードでは GitHub **Milestone** を「1スプリント = 1マイルストーン」として使う。

課題の階層は Jira と同じ2階層。**Story / Task / Bug は同格**で、どれもプロダクトバックログ
(milestoneなし)に並び、milestone を持ってスプリントに入る。**SubTask** はそのいずれかに
ぶら下がる子で、単独では存在しない。

| 種別 | 位置づけ | 例 |
|---|---|---|
| `type:story` | ユーザーに価値が届く機能要件 | 「会員として購入履歴を見たい」 |
| `type:task` | 技術的・運用的な作業 | 「Node 22 へのアップグレード」 |
| `type:bug` | 修正が必要な不具合 | 「特定条件で一覧が空になる」 |
| `type:subtask` | 上の3つから分解した作業の最小単位 | 「履歴APIの実装」 |

`type:kpt` はこの階層には**入らない** ── 振り返りで貼る付箋を Issue として表しただけで、
作業ではないのでボード・バックログ・完了件数のすべてから除外される。採用された Try だけが
`type:kpt` を外して `type:task` + `kaizen` になり、通常の流れに合流する。

### `/agile:init` が作るラベル一覧

`status` / `prio` / `type` / `kpt` / `points` の5系統と、単独の `kaizen` / `carried-over` で
**計21ラベル**。すべて `gh label create --force` で作成するので、再実行しても壊れない。

| 系統 | ラベル | 役割 | 主に張り替えるコマンド |
|---|---|---|---|
| status | `status:todo` `status:in-progress` `status:in-review` | ボードのカラム（無印＝Backlog、closed＝Done） | `/agile:board` |
| prio | `prio:high` `prio:mid` `prio:low` | バックログの優先度バケット | `/agile:backlog` |
| type | `type:story` `type:task` `type:bug` `type:subtask` `type:kpt` | 課題の種別（上の階層表を参照） | `/agile:issue` |
| points | `points:1` `points:2` `points:3` `points:5` `points:8` | ストーリーポイント（フィボナッチ） | `/agile:refine` |
| kpt | `kpt:keep` `kpt:problem` `kpt:try` | 振り返りの付箋の所属バケット | `/agile:retro` |
| — | `kaizen` | 振り返りで採用された改善タスクの目印 | `/agile:retro` |
| — | `carried-over` | 前スプリントの積み残し。次回プランニングで再評価する | `/agile:sprint-close` → `/agile:sprint-start` |

**`points:*` は任意。** 付いていれば、バックログのバケット合計（`/agile:backlog`）、
過去スプリントからのベロシティ算出（`/agile:sprint-start`）、消化ポイントの集計
（`/agile:sprint-close`）に使われる。付いていなくても件数ベースで動くので、
ポイント見積もりをしないチームはそのままで構わない。

**プロダクトバックログにサブタスクは置かない。** sprint モードでは、分解できるのは
**そのスプリントに入った（milestone を持つ）課題だけ**に制限している（先のことまで
分解するとムダになるため）。kanban モードにはこの制限は無く、いつでも分解できる。

日々動かす作業の単位は**サブタスク、および分解されていない Task / Bug**。
価値が届いたかの単位は**ストーリー**。ボードでは親子でネスト表示し、全サブタスクが閉じたら
親の In Review 前進を*提案*する（AC/DoDの確認が要るため自動では動かさない）。

## Kanban モードの流れ

sprint モードと違い、**計画・振り返りの区切りが無い**。代わりに以下の合図で流れを保つ。

| 合図 | 設定（`.agile/config.yml`） | 動作 |
|---|---|---|
| 補充（Replenishment） | `wip_limit.todo_min`（既定 2） | To Do が下回ると `/agile:board` が「`/agile:backlog` から補充しますか？」と促す |
| WIP 制限 | `wip_limit.doing` / `review` | 超過を警告。カウントは作業単位（容器である Story と分解済みの親は数えない） |
| 滞留の検知 | `stale_days`（既定 7） | In Progress/In Review にその日数だけ留まっているものを警告。**その列にいる時間**で測る（記録しているバックエンドの場合＝Jira）。記録が無い場合は最終更新時刻で代用し、そう明示する（GitHub） |
| 改善ループ | — | `/agile:retro` を**自分で決めた周期**で回す（区切りが無いので、決めないと回らない） |

両方の設定キーは省略可能で、既存の `.agile/config.yml` にこれらが無くても既定値で動く。

## `experimental:` ブロック

`.agile/config.yml` の `experimental:` は**お試し中の設定**を置く場所。ここのキーは
**将来のバージョンで予告なく仕様が変わる、あるいは消える**。試したい規律を早く出すための
場所であり、消えた場合も既定の挙動に戻るだけで、Issue・ラベル・マイルストーンには影響しない。
定着したものは上の階層へ移す（そのときは移行方法を CHANGELOG に書く）。

| キー | 既定 | 動作 |
|---|---|---|
| `require_subtasks_done` | `false` | `true` にすると、未完了のサブタスクが残っている親（Story/Task/Bug）を Done にできなくなる。ボード UI のボタン・ドラッグ、`/agile:board`、API のすべてで効く |

既定が `false` なのは Jira に合わせているため（Jira も既定では親を閉じられ、止めたい場合に
ワークフローのバリデータを足す）。なお **`false` でも、完了済みの親に未完了のサブタスクが
残っていればカードに ⚠ が出る**。これは設定に関わらず表示される ── GitHub 上で直接
クローズされた場合はどう設定しても止められないので、**防げないものは検知する**という分担。

## 課題テンプレート（`.agile/templates/`）

課題の本文は**フォームで組み立てず、テンプレートを下敷きに書く**。Jira の作成画面が
要約と説明の2つしか聞かないのと同じ理由で、ペルソナ・機能・価値・受け入れ条件…と
入力欄を細かく分けるほど、1段落を書くのに5つの箱を埋めることになり、起票の手間が増える。

`/agile:init` が `locale` に合わせて `story.md` / `task.md` / `bug.md` を書き出し、
以後は**チームが自由に編集できる**（`definition_of_done.md` と同じ扱い ── どう書くかは
チームの決めごとであって、プラグインの決めごとではない）。ボードの「+ 作成」と
`/agile:issue` が同じファイルを読むので、画面から起票してもチャットから起票しても
本文の形が揃う。ファイルが無ければ locale の既定にフォールバックするので、
テンプレート導入前に初期化したプロジェクトでもそのまま動く ── ファイルを実際に置いて
編集したい場合は、**`/agile:init` を再実行**すれば足りないものだけが追加される。

編集画面は**本文をそのまま表示する**。分解して詰め直さないので、GitHub 側で書き足された
内容が保存で消えることがない。

## Issue 本文の構造（GitHub Issues の場合・`<!-- agile:* -->` マーカー）

Issue 本文のうち、**ツールが読み返す部分だけ**が HTML コメントのマーカーを持つ。GitHub 上
では何も表示されない。対象は2つだけで、どちらも**サブタスクに対してツールが自動で書く**
── 人が打つことはないし、テンプレートにも入っていない。

```markdown
<!-- agile:parent #12 -->   ← 親リンク。これが無いとカードが親から外れる
<!-- agile:detail -->       ← サブタスクの説明。編集の往復に使う
```

Story / Bug の本文は**ただの散文**で、誰も解析しない。だからマーカーも無い
（テンプレートは編集してもらう前提のファイルなので、読み手のいない不可視コメントを
置かない）。

マーカーを使わず自然言語を解析していた頃は、**本文の言い回しを変えるだけで関係が切れた**
（サブタスクが親から外れてスイムレーンから消え、WIP のカウントもずれる。**エラーは出ない**）。
マーカー方式にしたことで、**周囲の文章は自由に書き換えても・翻訳しても壊れない**。

`.agile/config.yml` の `locale`（`ja` / `en`）が決めるのは、**`/agile:init` が書き出す
テンプレートとラベル説明の言語**と、サブタスクの `## 詳細` 見出しの言語。読む側は
マーカーを見るので、本文の言語が混在していても解釈できる。

言語を増やすときに触るのは `server/templates.js` の `TEMPLATES` と
`server/issueBody.js` の `SECTION_HEADINGS` だけで、パーサ側には手を入れない。
往復の検証は `node server/issueBody.test.mjs`。

### 途中で `locale` を変えたら

**変えて構わない。** 固定運用にする必要はない。

- **既存 Issue はそのまま読める** ── 構造はマーカーが持っているため。日本語と英語が
  混在した状態でも、ボードの表示・親子関係・WIP カウントは正しく動く。
- **既存の本文は勝手に翻訳されない** ── 編集画面は本文をそのまま出し、そのまま保存する。
  分解して組み直さないので、書いたものが別の言語に置き換わることがない。
- 新しく作る Issue だけが新しい言語になる。ただし `.agile/templates/` は
  `/agile:init` が作ったきり自動では更新されないので、**言語を変えたらテンプレートは
  手で書き直す**（チームの資産なので、勝手に上書きしない）。

つまり技術的な制約は無く、残るのは「本文が混在すると人間が読みにくい」という運用上の
理由だけ。`/agile:init` が最初に言語を確認するのは、チーム内の表記を揃えるためであって、
**あとから変更できないという意味ではない**。

## 前提

| バックエンド | 必要なもの |
|---|---|
| GitHub Issues | `gh`（GitHub CLI）がインストール・`gh auth login` 済み。対象プロジェクトに GitHub リモートがあること |
| Jira | `acli`（[Atlassian CLI](https://developer.atlassian.com/cloud/acli/)）がインストール・`acli jira auth login --web` 済み。ボードのURL |

どちらも **MCP は使わない**（コンテキスト消費ゼロ・決定的）。

## 使い方（利用側プロジェクトで）

```shell
# 初回のみ: マーケットプレイスを登録
/plugin marketplace add mi-snow7/agile-inspector

# プラグインを導入（scope は project 推奨）
/plugin install agile@agile-inspector
/reload-plugins

# プロジェクトを初期化して使い始める
/agile:init          # ラベル作成＋.agile/config.yml 生成＋DoD 合意
/agile:board            # モードに応じたボードを画面で開く＋テキストで要約
/agile:board #12 を doing に   # 対象が明確な移動はテキストだけで完結（画面は開かない）
/agile:standup

# 課題の起票（種別は依頼文から判定される）
/agile:issue 追加: 会員として購入履歴を見たい、再購入をラクにしたいから   # → Story
/agile:issue 追加: Node 22 へのアップグレード                          # → Task
/agile:issue 追加: 検索結果が2ページ目から空になる                      # → Bug
/agile:issue #12 編集
/agile:backlog          # バックログを優先度順に一覧＋画面を開く
/agile:backlog #12 を high に
/agile:refine           # バックログ整理のセレモニー（分割・受け入れ条件/ポイント見積もりまで）

# kanban モードの場合（区切りが無いので、流れを保つ合図で回す）
/agile:board            # カンバンボードが開く。To Do の残量（補充の合図）と滞留も点検する
/agile:backlog          # To Do が減ったらここから補充（Replenishment）
/agile:retro            # 隔週など、周期を決めて振り返る（スプリント境界が無いので自分で決める）

# sprint モードの場合（1スプリントのサイクル）
/agile:sprint-start     # 計画：ゴールの草案 → 積み残し(carried-over)の再評価 → 選定 → ゴール確定 → 分解
# ...スプリント期間中は board / standup で進行...
/agile:sprint-close     # 終了：デモ用一覧＋フィードバック反映、振り返り(/agile:retro)、積み残しはバックログへ
/agile:sprint-start     # 翌営業日など改めて実行し、次のスプリントを計画
```

積み残しの課題は **必ずバックログを経由**し、次回の `sprint-start` で PO が
「そのまま次に入れる／後回し／分割・破棄」を選び直す（自動で次スプリントに直行させない・
DoD未達のままDoneにしない、という2つのNG対応を避ける設計）。

## 更新

配布側では、利用側に届けたい変更を push する前に
`plugins/agile/.claude-plugin/plugin.json` の `version` を上げる。

```shell
# 例: 0.2.0 → 0.2.1 → 0.2.2 …
```

利用側は次の2つ。

```shell
/plugin marketplace update agile-inspector
/reload-plugins
```

**バージョンを据え置いたまま push しても、利用側には届かない。** キャッシュは
`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` に展開されるため、
`version` が同じなら既存のキャッシュがそのまま使われる（board-ui を開き直しても
古い画面のまま、という形で現れる）。

## 各プロジェクトに作られる `.agile/`

```
.agile/
  config.yml               # mode(kanban|sprint), backend, locale, capabilities,
                            # retro.board, WIP上限/To Do下限/滞留日数, sprint.current のみ
                            # ※ タスクデータは持たない（正はバックエンド側）
  definition_of_done.md    # チーム共通のDoD（全課題に共通の完了基準）。/agile:init で合意、/agile:retro で随時見直し
  templates/               # 新しい課題の書き出し。/agile:init が locale に合わせて作成し、以後チームが編集する
    story.md               # ボードの「+ 作成」と /agile:issue の両方がこれを読むので、
    task.md                # どちらから起票しても本文の形が揃う
    bug.md
  retro/
    2026-08-11.md          # 振り返りの議事録（Keep/Problem/採用したTry/見送り）。/agile:retro が回ごとに書く
```

**`.agile/` は git にコミットする。** 中身は個人設定ではなく**チームの合意事項**（WIP上限・
DoD・スプリント期間・言語）なので、追跡しないとクローンした人が別々の値で再初期化することに
なる。特に DoD は「全課題に共通の基準」という定義そのものが成り立たなくなる。

`sprint.current` だけはスプリントごとに書き換わるため、`/agile:sprint-start` /
`/agile:sprint-close` のたびに1行の差分が出る（「Sprint 6 が始まった」というプロジェクトの
実際の履歴なので、これは残してよい）。

DoD（Definition of Done）とAC（Acceptance Criteria / 受け入れ条件）は別物として扱う。

| | 対象 | 中身 | 置き場所 |
|---|---|---|---|
| DoD | 全課題に共通 | 品質・技術的な合格基準（テスト・レビュー等） | `.agile/definition_of_done.md`（`/agile:init`で合意、`/agile:retro`で見直し） |
| AC | 課題ごと | ビジネス・機能的な満足基準 | 各 Issue の本文（`/agile:issue`） |
